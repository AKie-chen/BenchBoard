探针源码：`tools/probes/k6_firehose_bench.cpp`（可自行复跑）

| 场景 | 行速率 | 字节速率 | `readyRead` 回调次数 | 平均行/次 | 单次回调最大耗时 | 回调累计占墙钟 |
| --- | --- | --- | --- | --- | --- | --- |
| A：8 VU / 8s 打本机 HTTP 服务 | 15,632 行/s | 3.60 MB/s | 7,101 | 21.1 | 2.21 ms | **1.17%** |
| B：8 VU / 5s 打死目标（连接秒拒） | **42,867 行/s** | **10.79 MB/s** | 19,791 | 18.1 | 0.39 ms | **3.43%** |

**结论（限 Release 构建）：管道读取 + 事件分发这一层，主线程扛得住，QThread 可以砍掉。**

**根因**（这条比数据本身重要）：`readyRead` 是**按缓冲区批量投递**的，不是每行触发。
4.2 万行/秒只对应约 2,400 次回调/秒 —— 所以 3.43% 的占用是合理的。

**反过来说**：如果你按很多教程写的"每读到一行就 `emit` 一个信号 + 刷新界面"，
就变成 4.2 万次/秒的函数调用 + 重绘，**必卡**。这条纪律比"用不用线程"更关键。

## 3. Qt / 构建陷阱

### 3.1 Qt Charts 崩溃（A/B 对照实测）

**症状**：链接通过、编译通过，运行时**段错误**。

**根因**：`QChartView` 的 `QGraphicsScene` 通过 `addItem` 接管了 `QChart` 的所有权；
`chart->addSeries()` / `chart->addAxis()` 同样接管 series 与 axis。
**栈对象析构后 scene 仍持有悬垂指针** → 崩溃。

**A/B 对照结果**

| 版本 | 分配方式 | 退出码 | 结论 |
| --- | --- | --- | --- |
| `charts_only` | `QChart chart;`（栈） | **139** | 崩溃 |
| `charts_heap` | `QChart *chart = new QChart();`（堆） | **0** | 正常 |

**规则**：`QChart` / `QLineSeries` / `QValueAxis` **全部 `new`**。
注意 `QChartView` 本身不接管 chart 的所有权，但 scene 会——所以 chart 必须活得比 view 久。

**M4 复测（2026-09-23，`tools/probes/m4_skeleton_check_run.sh`）—— 把崩溃点精确到了那一行**

上面那张表只说了"栈版会崩"，但没说**崩在什么时候**。复测时在栈版里插了 4 个路标，
并把 stdout 设为**无缓冲**（`setvbuf(stdout, nullptr, _IONBF, 0)`），结果：

```
  [栈版] ① 栈对象已建好（chart / series / axisX / axisY）
  [栈版] ② 已装配：addSeries / addAxis / attachAxis
  [栈版] ③ view.show() 返回了
  [栈版] ④ processEvents 也过了，函数即将返回，栈对象将被析构…
stack exit=127
```

**④ 之后没有 ⑤** —— 说明崩溃点**精确落在"函数返回、栈对象析构"那一刻**，
而不是 `addSeries`、不是 `show()`、也不是 `processEvents()`。
这解释了为什么这个 bug 最迷惑人：**崩溃现场离肇事代码隔着一个 `return`**，
栈回溯里看到的是 scene 的绘制代码，而真正写错的是几层之外的变量声明方式。

复测时的两条工程经验：

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| stdout 块缓冲 | 进程被异常终止时**整个缓冲区丢失** → "程序什么都没打印就没了"，容易误判成"根本没跑起来" | 探针里 `setvbuf(stdout, nullptr, _IONBF, 0)`，崩溃前的路标全部保留 |
| 退出码不是 139 | Windows 上崩溃的 `$?` 是 **127**（139 = 128+SIGSEGV 是 Unix 的记法） | **别用具体数字判断崩没崩，用"非 0"**；`139` 只在本项目早期的 Unix 式记录里出现 |

**M4 复测 ②（2026-09-24，`tools/probes/m4_stack_owner_probe_run.sh`）
—— 逐段切开所有权链：到底【哪一个】对象上栈才会崩？**

上面两条只测了"全栈 vs 全堆"，于是规则被写成"`QChart` / `QLineSeries` / `QValueAxis`
**全部必须 new**"。**这个说法过头了。** 把链逐段切开、一次只让一个对象上栈：

| 模式 | 谁在栈上 | 退出码 | 结果 |
| --- | --- | --- | --- |
| `heap` | —（基线） | 0 | 不崩 |
| `stack-all` | chart + series + axisX + axisY | **139** | **崩** |
| **`stack-chart`** | **只有 chart** | **139** | **崩** |
| `stack-series` | 只有 series | 0 | 不崩 |
| `stack-axisY` | 只有 axisY | 0 | 不崩 |
| `stack-axisX` | 只有 axisX | 0 | 不崩 |

**崩与不崩，只由 `chart` 一个人决定。** series 和两个轴单独上栈**都不会崩**。

**为什么？** 在 `stack-axisY` 里插一行打印 `chart->axes()`：

```
  [build-stack-axisY] axisY 还在作用域内：chart->axes()=2
  [build-stack-axisY] axisY 已析构：chart->axes()=1     ← 它自己摘牌了
```

轴析构时**把自己从 chart 的轴列表里摘掉了**（走 QObject 父子机制 + chart 自己的 remove 逻辑），
chart 手里没有悬垂指针。series 同理。

而 `chart` 是被 **`QGraphicsScene::addItem()` 用裸指针**持有的 —— 它不是 QObject 的父子关系，
chart 析构时**没人替它摘牌**，scene 手里留下悬垂指针。崩点在**此后的第一次绘制**：

```
  [build-stack-chart] 即将返回 —— 栈上的 chart 就要析构
  [main] ① build 已返回（栈对象如有则已析构）
  ← ② "show + processEvents 通过" 这一行【没有打印】→ 崩在这里
```

> **崩点为什么会"漂移"？** 上面 `m4_skeleton_check` 的栈版崩在**析构那一刻**，
> 本探针却崩在析构**之后**的 `show()`。差别在**绘制什么时候发生**：
> 前者在函数里已经 `show()` + `processEvents()` 过（绘制发生过），后者没有。
> **两者都是"访问已析构的 chart"** —— 触发时机取决于下一次绘制什么时候来。
> 记结论时别记成"崩在 XXX 行"，要记成"**栈上的 chart 一析构，view 手里就是炸弹，
> 下次绘制引爆**"。

**★ 由此得到一条能跨场景复用的规律（比"必须 new"值钱得多）：**

| 被持有的对象 | 谁持有它 | 析构时摘不摘牌 | 结果 |
| --- | --- | --- | --- |
| 栈 `QVBoxLayout` | `central`（**QObject 父子**） | ✅ 摘（children 4→3，见 3.13） | 不崩 |
| 栈 `QValueAxis` / `QLineSeries` | `chart`（**QObject 父子** + 列表） | ✅ 摘（`axes()` 2→1） | 不崩 |
| 栈 `QChart` | `QGraphicsScene`（**裸指针**） | ❌ 没人摘 | **崩 139** |

> **"能不能上栈"不取决于"有没有被接管"，而取决于"接管它的是不是 QObject 的父子机制"。**
> 是 → child 析构时自己摘牌，安全；不是（裸指针容器）→ 悬垂 → 崩。
> 判断就三步：**① 谁持有它 ② 谁先走 ③ 走的时候摘不摘牌。**

**对写码的指导**：虽然"只有 chart 不能上栈"，但**别拿这条去省事** ——
轴/series 要长期被 `attachAxis` 引用，一旦有人把 `chart` 挪进同一个作用域（很容易），就一起崩。
**规则照旧写"这条链上全部 `new`"**，只是要知道：那是纪律，不是机制边界。

### 3.2 MSVC 中文乱码

**症状**：源码里的中文（注释、界面字符串）在运行时显示为乱码。

**根因**：源码是 UTF-8 无 BOM，而 MSVC 按系统 ANSI 代码页（简体中文环境是 GBK / CP936）解码。

**修复**：`CMakeLists.txt` 里加

```cmake
if (MSVC)
    add_compile_options(/utf-8)
endif()
```

**验证方式**（别靠肉眼看控制台，控制台本身还会再乱一次）：
把输出重定向到文件，再按两种编码解码对比。
加上 `/utf-8` 后"结果"的字节是 `E7 BB 93 E6 9E 9C`（UTF-8），这是判据。

### 3.3 `-DCMAKE_PREFIX_PATH` 路径形式

| 写法 | 结果 |
| --- | --- |
| `-DCMAKE_PREFIX_PATH=/e/Qt/6.10.2/msvc2022_64` | ❌ `Could not find a package configuration file provided by "Qt6"` |
| `-DCMAKE_PREFIX_PATH=E:/Qt/6.10.2/msvc2022_64` | ✅ |

原生 `cmake.exe` 不认识 MSYS 的 `/e/` 路径形式。同理，`-S` 给的源码目录也必须是
`E:/BenchBoard` 而非 `/e/BenchBoard`（否则报 "The source directory does not exist"）。

### 3.4 PATH 被 MSYS 污染导致链接失败

**症状**：`ld.exe: cannot find /nologo /out:...`

**根因**：PATH 里 MSYS 的 `/usr/bin/link.exe` 顶掉了 MSVC 的 `link.exe`，
MSVC 的参数被 MSYS 的 link 当自己的参数解析。

**修复**：PATH 只保留 MSVC + SDK + CMake + Ninja + System32。
`tools/build.sh` 里的 `CLEANPATH` 就是干这个的，**不要图省事直接 `cmake`**。

### 3.5 vcvars 加载失败

**症状**：`Enter-VsDevShell` 报 `Path/PATH` 大小写重复键。

**处理**：不调 vcvars，手工拼 `INCLUDE` / `LIB` / `PATH`（见 `tools/build.sh`）。

### 3.8 头文件包含的三种写法 —— 都能编译，代价差一倍

Qt 的 include 路径由 `Qt6::Widgets` 自动提供 4 个目录（实测提取自 `build.ninja`）：

```
E:\Qt\6.10.2\msvc2022_64\include
E:\Qt\6.10.2\msvc2022_64\include\QtCore
E:\Qt\6.10.2\msvc2022_64\include\QtGui
E:\Qt\6.10.2\msvc2022_64\include\QtWidgets
```

**因为 `include\QtWidgets` 本身在路径里，所以三种写法都命中同一个文件**：

| 写法 | 实际命中的文件 | 该文件大小 |
| --- | --- | --- |
| `#include <QPushButton>` | `include\QtWidgets\QPushButton` | 49 B（转发头，里面只有一行 `#include "qpushbutton.h"`） |
| `#include <QtWidgets/QPushButton>` | 同上，**与上面完全等价** | 49 B |
| `#include <QtWidgets>` | `include\QtWidgets\QtWidgets` | 6574 B（**模块总头，内部包含 123 个 include**） |

同一次改动的编译实测（MSVC 14.44 / Release / 单文件重编）：

| 写法 | 牵扯头文件数 | 其中 Qt 头 | 编译耗时 | .obj |
| --- | --- | --- | --- | --- |
| `<QPushButton>` 逐类 | **441** | 303 | **4.3 ~ 4.8 s** | 1 KB |
| `<QtWidgets/QPushButton>` | 441 | 303 | 4.3 s | 1 KB |
| **`<QtWidgets>` 模块总头** | **851** | 673 | **7.0 ~ 7.1 s（+47%）** | 5 KB |
| `<QtCore> + <QtGui> + <QtWidgets>` | 851 | 673 | 7.0 s | 5 KB |

> 模块总头还会经 `QtWidgetsDepends` 拉进 `QtCore` + `QtGui` 两个总头，依赖直接翻倍。

**纪律**：`.h` 里逐类包含（`<QPushButton>`），不要用模块总头。原因是 `.h` 会被多个 `.cpp` include —— `.h` 里多拉 410 个头，**每个包含它的 `.cpp` 都要承担**。

**什么时候不能只靠前置声明**（实测 `error C2027` + `error C2061`）：

| 场景 | 例子 | 为什么必须 include |
| --- | --- | --- |
| 基类 | `class MainWindow : public QMainWindow` | 需要完整定义才能继承 |
| 值语义成员 | `QProcess m_engine;`（非指针） | 需要 sizeof 与构造/析构 |
| **槽签名里的嵌套类型** | `QProcess::ExitStatus` | **前置声明后是不完整类型，访问不了嵌套类型** —— 这正是 `MainWindow.h` 里必须 `#include <QProcess>` 的原因 |
| 模板实参 | `QVector<QPoint>` | 实例化需要完整定义 |

反例：成员是**指针**时前置声明就够（所以 `MainWindow.h` 里那 6 个控件指针可以用 `QT_BEGIN_NAMESPACE class QComboBox; QT_END_NAMESPACE` 前置声明）。

### 3.9 `QProcess` 初始化位置 —— 两个「一按就崩 / 压测在跑但界面空白」的坑

M2 实操时两个都踩到了，一个是崩溃、一个是**静默**失败，后者更贵。

| # | 错误写法 | 症状 | 根因 |
| --- | --- | --- | --- |
| 1 | `QProcess *m_engine = new QProcess(this);` | 点「开始压测」**立刻崩**：`0xC0000005: 读取位置 0x8 时发生访问冲突`，崩溃点在 `Qt6Core.dll` | 加了类型名 → 变成**局部变量**，把成员 `m_engine` **遮蔽（shadow）** 掉。成员仍是 `nullptr`，`setProgram()` 去读 `this->d_ptr`（对象内偏移 8 字节）→ 读地址 `0x8` |

| --- | --- | --- | --- | --- |
| 修前 | **11**（只有"按钮通了"+"引擎已启动："） | ❌ | ❌ | ✅ 产出 4111 B |
| 修后 | **2,834** | ✅ | ✅ | ✅ 产出 |

> 注意第二行：**`summary.json` 有产出**恰恰是"看起来没问题"的假象来源。判断依据只能是日志区有没有数据。

**口诀**：`m_engine = new QProcess(this);` 必须是构造函数里**第一件事**，且**不能带类型名**。

**编译器其实警告过**：`/W4` 下 MSVC 会报 `C4458: declaration of 'm_engine' hides class member`。
这类警告不是噪声，它直接指向 bug —— 别养成"能跑就行"的习惯。

### 3.10 k6 JSON 流的首包长什么样（M3 解析器要按这个写）

`-o json=-` 的开头**不是**直接进 Point，而是先成对出现 `Metric` 声明行。实测首包前 4 行：

```jsonc
{"type":"Metric","data":{"name":"http_reqs","type":"counter","contains":"default",...}}
{"metric":"http_reqs","type":"Point","data":{"time":"...","value":1,"tags":{...}}}
{"type":"Metric","data":{"name":"http_req_duration","type":"trend","contains":"time","thresholds":["p(95)<500"],...}}
{"metric":"http_req_duration","type":"Point","data":{"time":"...","value":3.8672,...}}
```

→ M3 的切行解析器必须**先判 `type` 是否为 `"Point"`**，`Metric` 行直接跳过。

顺带一个性能基线：5 VU / 10s 打本机 `python -m http.server`，实测收到 **161,158 行 / 47.5 MB**
（≈16,116 行/s、4.75 MB/s）—— 与第 1 节的 8VU 基线同量级。

### 3.11 M3 写解析器前必须先知道的 9 条（全部实测，2026-09-22）

这一节是 M3 的**实现前提**。8 条里有 3 条会直接改掉你原本的写法。

#### ① 原始流里的 counter 是【增量】，summary 里是【累计】—— 语义相反

```
流里  http_reqs 的值分布：{1: 142}      ← 142 个点，value 全是 1
流里  iterations 的值分布：{1: 141}
```

→ 原始流的 counter 发的是 **delta（每次 +1）**，必须 `+=`；直接赋值永远得到 1。
而 `summary.json` / REST API 里 `http_reqs.count` 是**累计值**，可以直接用。
两处语义相反，这是写报告时最容易产出"总请求数 = 1"的原因。

#### ② `vus` 极稀疏 —— 2000 行原始流里一条都没有

`grep -c vus tests/corpus/k6_stream_sample_2k.jsonl` → **0**。
那 2000 行 ≈ 14 次迭代、不到 1 秒，而 vus 是每秒采一次。
→ 它是 gauge，用**赋值**不是累加；而且做曲线时**必须前向填充**（M4 会踩）。

#### ③ `--quiet` 关不掉结尾的人类摘要，它走 stdout 且混在 JSON 流末尾

```
--quiet + -o json=-        → stdout 29,891 行，其中【23 行不是 JSON】，stderr 0 行
非 JSON 的行长这样：
  █ THRESHOLDS
    http_req_duration
    ✓ 'p(95)<500' p(95)=1.71ms
  █ TOTAL RESULTS
    http_reqs......................: 2131   1064.586212/s
```

→ 它们必然解析失败，**这是正常现象**。解析器只能 `++parseErrors` 然后返回，
不能 throw、不能中断、不能弹框。
**附带证明 `.err` 是空的** —— 所以 M2 的"必须读 stderr"是为了防管道堵死，
不是为了看报错（k6 的报错在 `--quiet` 下也基本不往 stderr 写）。

#### ④ `--summary-mode disabled` 能关掉摘要，但会【连 `--summary-export` 一起干掉】

| 参数组合 | stdout 非 JSON 行数 | `--summary-export` 文件 |
| --- | --- | --- |
| `--quiet`（默认 full） | 23 | ✅ 3,710 B |
| `--quiet --summary-mode compact` | 23 | ✅ 3,673 B |
| `--quiet --summary-mode full` | 30 | ✅ 3,833 B |
| **`--quiet --summary-mode disabled`** | **0** | ❌ **没有产出** |

→ **这条路堵死**：summary-export 是唯一能拿到 p99 的通道，不能被干掉。
只能让解析器容忍脏行（见 ③）。
另外：**`--no-summary` 这个参数不存在** —— 实测报
`level=error msg="unknown flag: --no-summary"`，脚本直接中断。
（网上不少文章写 `--no-summary`，那是旧版本语义或直接是错的。）

#### ⑤ `thresholds` 子对象里的布尔值：`true` = **被突破**，不是"通过"

同一个值挂两个方向相反的阈值，实测：

```
p(95)=1.845060 ms
thresholds = {"p(95)<100000": false, "p(95)<0.0001": true}
```

→ `true` 表示**该阈值被突破（不通过）**。同时 k6 的退出码：

| 情况 | `exitStatus` | `exitCode` |
| --- | --- | --- |
| 全部通过 | `NormalExit` | `0` |
| 有阈值被突破 | `NormalExit` | **`99`** |
| 被 `kill()` | `CrashExit` | `62097`（无语义） |

→ 结论仍是用 `exitStatus` 判"是不是被强杀"；`exitCode == 99` 是**阈值不达标**的合法信号，
报告里可以拿它做"压测通过 / 不通过"的判定抓手。

#### ⑥ `http_req_failed` 的 `passes` / `fails` 是**反的**（最坑的一条）

```
全成功的一轮：http_req_failed = {"passes": 0,     "fails": 2532, "value": 0}
全失败的一轮：http_req_failed = {"passes": 10659, "fails": 0,    "value": 1}
真实一轮     ：http_req_failed = {"passes": 7621,  "fails": 4255, "value": 0.6417}
               总请求 11876 = 7621 + 4255；  7621 / 11876 = 0.6417 ✓
```

→ 对 `http_req_failed` 这个 rate 指标：
- `passes` = **失败**请求数（value ≠ 0 的样本数）
- `fails`  = **成功**请求数
- `value` = 失败率 = `passes / (passes + fails)`

**不要**写 `成功率 = fails / (passes+fails)` 之外的任何变体 —— 直接把 `passes`
当"通过数"会得到 64% 成功率（实际是 36%）。M5 写汇总面板时会用到。

#### ⑦ `-e KEY=VALUE` 确实能让界面输入框生效（差分实测）

`examples/script_demo.js` 里改成 `const BASE_URL = __ENV.BASE_URL || 'http://127.0.0.1:8899/'` 后：

| 跑法 | 结果 |
| --- | --- |
| `-e BASE_URL=http://127.0.0.1:8899/`（服务开着） | 2,532 请求，checks 全过 |
| `-e BASE_URL=http://127.0.0.1:9999/`（端口关着） | 10,833 请求，checks **全败** |
| 不传 `-e` | 回落到脚本默认值（打到 8899，服务已关 → 全败） |

→ 第二行是关键证据：换个端口结果就翻转，说明 `-e` 真的被用上了。
同时 `--vus` / `--duration` 也覆盖脚本 `options`（实测 `vus.max` 跟着命令行变）。

#### ⑧ `QElapsedTimer::elapsed()` 在无效状态下返回垃圾值

```
未 start() / 已 invalidate() 时：elapsed() = -9223352315 ms   ← 不是 0
```

→ 读它之前必须 `if (m_clock.isValid())`。
`MetricsAggregator::refreshElapsed()` 里那个判断就是为这条准备的；
没有它，两次压测之间状态栏会闪出一个天文数字。

#### ⑨ 语料的期望值（拿它对账，别靠肉眼看）

回放 `tests/corpus/k6_stream_sample_2k.jsonl` 的**正确结果**：

| 计数 | 值 | 交叉校验 |
| --- | --- | --- |
| `lines` | 2000 | = `metricDecls` + `points` ✓ |
| `metricDecls` | 14 | = k6 的指标个数 |
| `points` | 1986 | 1986 / 142 ≈ 14.0（每迭代 14 个 Point）|
| `requests` | 142 | = `iterations` 数 |
| `failedCount` | 0 | 语料里全是成功请求 |
| `parseErrors` | 0 | 这份语料没有尾部摘要 |

「`lines` 必须等于 `metricDecls + points`」是一条**免费的自检**：
对不上就是切行或分类写错了。这份语料末尾有换行，所以 `m_pending` 应该是空的。

⚠️ **但别把 "14" 记成常数** —— 见 3.12 ①。

### 3.12 M3 验收阶段的新实测（2026-09-23）

#### ① 语料 14 个指标声明，真实跑是 **16** 个

同一个脚本、同一个 k6 版本，两边的声明数不一样：

| 来源 | 行数 | `metricDecls` | 差异 |
| --- | --- | --- | --- |
| 语料 `k6_stream_sample_2k.jsonl` | 2,000 | **14** | — |
| 真实 10 秒 8 VU 跑 | 20,821 | **16** | 多 `vus`、`vus_max` |

原因：**指标声明是懒发的** —— 某个指标第一次产出数据时才发那一行。
`vus` / `vus_max` 是 gauge，k6 **每秒才采一次**，2,000 行的短样本（≈ 1 秒）里还没轮到发。

所以正确的说法不是"k6 有 14 个指标"，而是 **「声明行数 == 该次跑实际出现的指标个数」**，
而且这 16 个的去重后数量恰好也等于 16（可用来自校验）。

漏掉的代价：如果按"恒等于 14"去写校验，真实跑必然误报。

#### ② 真实跑的三个计数（10 秒 / 8 VU / 打本机 http.server）

| 计数 | 值 | 交叉校验 |
| --- | --- | --- |
| `lines` | 20,821 | — |
| `points` | 20,782 | `20782 + 23 + 16 = 20821` ✓ |
| `metricDecls` | 16 | 见 ① |
| `parseErrors` | 23 | 尾部人类摘要（见 3.11 ③） |
| `requests` | 1,483 | **= `summary.json` 的 `http_reqs.count`** ✓ |
| 字节 | 4.8 MB | — |

**「请求数与 `summary.json` 精确相等」是本项目最有价值的一条端到端对账** ——
它一次同时验证了三件事：`+=` 增量语义对、切行没丢数据、聚合器与 k6 的统计口径一致。

#### ③ 「漏一行但全绿」—— 只能靠断言抓，肉眼一定漏

实测踩到的 bug（M3 验收时被 A3 断言逮到）：

```cpp
if (type != QStringLiteral("Point")) { return; }
++m_stats.points;          // ← 漏了这一行
```

后果：编译 **0 警告**、运行 **0 报错**、k6 进程正常、`summary.json` 正常产出、
状态栏**数字确实在跳**（请求数 1483 一路涨）、日志区进度行也正常滚动。
唯一的异常是"已采集 0 点"。

**为什么肉眼抓不到**：状态栏里的数字是活的，人看到"数字在动"就默认它是对的。
**为什么断言抓得到**：A3 断言写的是"结束时点数 > 0"，一个布尔，跟数字动不动无关。

结论：凡是"漏了也不报错"的代码，就必须有一条独立的计数守恒断言兜着。
本关的守恒式是 `lines == points + metricDecls + parseErrors`。

#### ④ 切碎喂语料 = 半行残留路径的正确性证明

`corpus_replay_probe` 用两种粒度喂同一份语料，结果必须**逐字段一致**：

| 喂法 | 目的 | 结果 |
| --- | --- | --- |
| 一次 `feed(全部 477,903 字节)` | 基线 | 2000 / 14 / 1986 / 142 |
| 每 **7 字节** `feed()` 一次 | 让管道边界**必然**断在行中间 | 2000 / 14 / 1986 / 142 ✓ |

7 字节一批意味着每行 JSON（约 240 字节）要被拼 34 次，
`m_pending` 的"拼接 → 找最后一个 `\n` → 切除"要被跑 6.8 万次。
两者结果完全一致，半行残留逻辑才算被证明是对的 ——
**这比"跑真流看着数字在涨"强得多，因为真流的边界断点不可控、不可复现。**

边界组另外 5 条也全过：脏行只计数不中断、半行挂起 20 字节、
下半行送达后补成完整行（`vus=7` 正确赋值）、`reset()` 清空残留、`stop()` 后 `elapsedMs` 定格。

#### ⑤ 「进程被强杀后不产出 summary」在 real 场景下的兜底意义

`m3_e2e_probe_run.sh stop`（第 4 秒点停止）跑完：`reports/summary.json` **不存在**，
但聚合器已经攒到 **6,474 点**。这就是 M3 存在的全部理由 ——
**用户中途停止时，实时聚合的数据是他唯一拿得到的数据。**

### 3.13 栈对象挂了 parent —— 到底崩不崩？（A/B/C 实测，2026-09-23）

**问题**：`MainWindow.cpp:86` 是 `QVBoxLayout *mainLayout = new QVBoxLayout(central);`。
改成栈对象 `QVBoxLayout mainLayout(central);`，是**崩**，还是只是**布局失效**？

流传着两种说法，正好对立：① 骨架注释（`MainWindow.cpp:84-85`）说"控件会瞬间失去布局"；
② "`central` 析构时会 delete 子对象，而子对象在栈上 → double free → 崩"。

实测见分晓（`tools/probes/stack_layout_probe_run.sh`，Qt 6.10.2 / MSVC Release）：

| 形态 | `central` 的生命期 | 栈 layout 的生命期 | 结果 |
| --- | --- | --- | --- |
| A `heap`（基线） | 堆 | —（也是堆） | 控件被撑开，`delete central` OK，**exit 0** |
| B `stack-owner-alive` | 堆，**比栈对象活得久** | `buildUi()` 返回时先走 | **不崩，exit 0** |
| C `stack-owner-dead` | **先被 `delete`** | 稍后才走 | **崩，exit 127** |

#### B 才是本项目的真实形态 —— 结论是「不崩，但界面是散的」

`central = new QWidget(this)` 经 `setCentralWidget` 被 QMainWindow 接管，**活到 MainWindow 析构**；
而栈 layout 在 `buildUi()` 返回时就先走了。实测：

```
  [in-scope]     central->layout()=0000004010EFF7C8   children=4
  -- 作用域结束，栈 layout 已析构 --
  [out-of-scope] central->layout()=0000000000000000   children=3
  >> delete central（若 double free，就崩在这里）
  delete central -> OK, NO CRASH
```

三条关键事实：

1. **不崩**。`delete central` 正常返回。
2. 栈 layout 析构时**把自己从 central 的 children 里摘掉了**（4 → 3），
   所以 central 之后析构根本不会碰它 → **没有 double free**。
3. Qt 还把它清成了 **`nullptr`**（不是留个悬垂指针）→ `central->layout() == nullptr`。

**真正的后果是布局失效**，但现象分两种时序，**本项目踩的是第二种**：

| 时序 | 现象 |
| --- | --- |
| layout 活着时 `show()` 过 | 控件**已经摆好位**，只是之后**不再跟随窗口缩放** |
| `show()` 在 layout 析构**之后**（← **本项目**：`buildUi()` 里没有 `show()`） | 控件**从未被摆过位** |

第二种实测（`stack-show-after` 模式）：

```
  after-show: btn1=(0,0 80x20)  btn2=(0,0 80x20)  label=(0,0 24x12)
```

三个控件**全叠在左上角**、尺寸全是 sizeHint —— 这就是骨架注释说的"**一堆叠在一起的散件**"。
**注释是对的，只是没说清它为什么不崩。**

#### 和 3.1（Qt Charts 栈分配崩溃）对照 —— 同样是"栈对象被接管"，结果相反

| | 3.1（`QChart` 栈） | 3.13-B（`QVBoxLayout` 栈） |
| --- | --- | --- |
| 谁持有它 | `QGraphicsScene` | `central` |
| **怎么持有的** | **裸指针**（`addItem`） | **QObject 父子**（children 列表） |
| 栈对象是否先析构 | 是 | 是 |
| **析构时摘不摘牌** | ❌ 没人摘 | ✅ 自己摘（children 4→3） |
| 结果 | **崩（139）** | **不崩（0）** |

**两者"谁先析构"是一样的，结果却不同** —— 所以"父对象活得久就不会崩"这种说法并不成立。
差在**接管它的是不是 QObject 的父子机制**：

- `QObject` 的 parent-child 是**条件所有权**：child 先析构时会**自己摘牌**（实测 children 4→3），
  parent 之后就不再 delete 它 → 栈对象能安全退场。
- `QGraphicsScene` 对 item 是**裸指针持有**（2026-09-24 已实测坐实，见 3.1「M4 复测 ②」）：
  chart 析构时**没人替它摘牌** → scene 手里留悬垂指针 → 下次绘制崩（exit 139）。
  **这不是"所有权强弱"的差别，是"摘不摘牌"的差别** ——
  QObject 父子关系里 child 析构会自己摘牌，裸指针容器里没人摘。
  （实测：`QValueAxis` 和 `QLineSeries` 单独上栈**都不崩**，因为它们挂在 chart 上、走 QObject 父子；
  只有 `QChart` 上栈才崩。）

> **能记住的版本**：`QObject` 的父子不是"谁被谁删"，而是"**谁最后走谁负责**"。
> 栈对象先走 → 自己摘牌离场，安全；堆上的 parent 先走 → 栈对象被删一次、退出作用域再删一次 → 崩。
> **判断这类问题，先问"谁先析构"，再问"接管方是不是非删不可"。**

复现：`bash tools/probes/stack_layout_probe_run.sh`（跑 5 个模式：`heap` / `stack-owner-alive` /
`stack-owner-dead` / `stack-show-after` / `stretch-zero`）

### 3.14 不传拉伸因子时，多出来的高度归谁？（2026-09-23）

`addWidget(w)` 不传第二个参数 = `stretch = 0`。那窗口拉高时多出来的空间给谁？实测：

| 场景 | 结果 | 结论 |
| --- | --- | --- |
| a) 三个 `QPushButton`（垂直都**不是** Expanding），`central` 高 900 | 三个按钮**各 20px 高**，间距被撑到 227px（y = 212 / 439 / 666） | 没有 Expanding 控件时，多余空间**被平均分散到各 item 之间** |
| b) `QPushButton` + `QPlainTextEdit`（垂直 **Expanding**），`central` 高 900 | 按钮**还是 20px**，`QPlainTextEdit` 拿走 **852px** | 有 Expanding 控件时，多余空间**全归它**，其它 item 一点都不多拿 |

**所以规则是三级，不是一句"平均分配"：**

1. 有 `stretch > 0` 的 → 按 stretch 权重分；
2. 都没 stretch → 按 `sizePolicy`，**Expanding 的拿走全部**；
3. 连一个 Expanding 都没有 → 才**平均分散**（实测 a）。

**对本项目的意义**：`m_logView` 是 `QPlainTextEdit`，垂直就是 **Expanding**。
所以 `MainWindow.cpp:145` 那个 `1`（`addWidget(m_logView, 1)`）**在当前单图版本是冗余的** ——
不给 stretch 它也照样独吞全部额外高度（实测 b）。
它的真正作用要到 **M4 加进 `m_chartView`** 之后才显现：那时有两个 Expanding 抢空间，

### 3.15 火管吞吐与构建类型 —— "10 秒的测试跑了快一分钟"（2026-09-23，M4 开门阻塞）

**现象**（用户报告）：10s / 8VU 跑两次，两次都是"运行快一分钟才测完"；
启动后日志区打印 2KB 数据，界面就卡到什么都点不了。

**证据**（全量归档 `docs/evidence/m4/firehose_baseline_20260923.txt`）

| # | 测什么 | 结果 |
| --- | --- | --- |
| ① | k6 真实输出速率（stdout 重定向到文件，无读者瓶颈；死目标场景） | 2,137,971 行 / 530.8 MB / 10 s = **213,797 行/s、55.7 MB/s** |
| ② | 每请求采样行数（21:16 那次逐行统计） | 14 个指标 × 152,708 点 = **14.0 行/请求**，完全均匀 |
| ③ | `feed()` 全量解析 @ **Release** | **330,135 行/s / 82 MB/s** |
| ④ | `feed()` 全量解析 @ **Debug**（apps 侧实际构建） | **14,778 ~ 21,349 行/s / 3.7~5.4 MB/s** |
| ⑤ | Debug vs Release | **≈ 16 ~ 23 倍**（同进程 A/B：100,142 ms vs 6,476 ms） |
| ⑥ | 只解析 4/14 个指标（前缀白名单预筛） | Release **3.63×** / Debug **3.94×** |
| ⑦ | app 的构建类型与 Qt DLL 变体 | `CMAKE_BUILD_TYPE=Debug`；exe 依赖 `Qt6Cored.dll` / `Qt6Widgetsd.dll` |

**复现用户那次**：99,710 请求 × 14.0 行 = **139.6 万行 / ≈350 MB**。
按 ④ 的区间，app 在 10 秒里只能吃掉 14.8~21.3 万行，剩下 **118~125 万行**要再排
**56~84 秒** → 预测总时长 **66~94 秒**，用户实测"快一分钟"，落在区间内。

**根因**

1. **主因｜构建类型**：`tools/build.sh` 写死 `-DCMAKE_BUILD_TYPE=Debug`。
   Debug 配置下 Qt 的 CMake 包把 `Qt6::Core/Gui/Widgets` 映射到 **Debug 版 DLL**
   （已用 `strings BenchBoard.exe` 确认），叠加 MSVC `/Od` 与 debug CRT 的堆开销，
   解析路径慢 16~23 倍。**"主线程扛得住"这个结论只在 Release 下成立。**
2. **放大器｜没有积压上限、也没有任何提示**：`QProcess` 在 Windows 上用重叠 IO
   把管道往自己的内部缓冲里抽干，**不关心消费方进度**。所以 k6 全程不阻塞
   （它确实 10 秒跑完、summary 也正常写了），但 app 手里会攒下 ≤350 MB 未解析数据；
   而 `QProcess::bytesAvailable()` 这个数字界面上一个都没露出来 ——
   积压是**完全隐形**的，用户只能感觉到"卡"。
3. **附带缺陷｜错误路径静默**（独立于上面两条，见 3.16）：`MainWindow.cpp` 没有
   `connect(m_engine, &QProcess::errorOccurred, ...)`，于是 `FailedToStart`
   在界面上的表现是「日志区只有一行『引擎已启动：』+ 状态栏『引擎：运行中』+
   已跑秒数一直涨」，和"k6 在跑但没输出"**肉眼完全无法区分**，而且**永远停不下来**。

**修复**

| 优先级 | 改什么 | 依据 |
| --- | --- | --- |
| **必修（1 行）** | `tools/build.sh` 的 `-DCMAKE_BUILD_TYPE=Debug` → `RelWithDebInfo` | ④⑤：#5 单独就把过载从 ~10 倍降到 ~0.6 倍 |
| **纪律** | **验收探针的构建类型必须与 apps 侧一致** | `m3_e2e_probe_run.sh` 用 Release、app 用 Debug —— 这就是 M3 全绿而实机卡死的原因 |
| 建议 | 状态栏显示 `m_engine->bytesAvailable()` | 把隐形的背压变成可见数字；不显示就永远只能"感觉到卡" |
| 可选 | 前缀白名单预筛（⑥） | 再拿 3.6~3.9 倍；**但会打破守恒断言，见下** |

**⚠️ 顺带一条会咬人的副作用**：预筛之后 `points` 的含义从"所有 Point 行"变成
"我们关心的 Point 行"，M3 那条守恒式
`points + parseErrors + metricDecls = lines`
**就失效了**（实测：2,137,918 → 458,131）。
必须同步补一个 `skipped` 计数，把式子改成
`points + skipped + parseErrors + metricDecls = lines`。
不改断言就等于**主动丢掉了 M3 唯一能抓住"漏一行但不报错"的那道保险**（见 3.12 ③）。

### 3.16 `QProcess` 启动失败在界面上是静默的（2026-09-23 取证；故障本身是**临时**的，见末尾修正）

探针：`tools/probes/qprocess_start_check.cpp` + `qprocess_start_check_run.sh`
（把 `QProcess` 的每一个状态变化都打出来，包括 `errorOccurred`）

```
t=    0ms  [stateChanged]   Starting
t=   10ms  [errorOccurred]  FailedToStart  (pipe: 系统找不到指定的文件。)
t=   10ms  [stateChanged]   NotRunning
```

**同一个失败在真实 `MainWindow` 上的样子**（`firehose_ui_probe.cpp` 抓的截图）：

| 界面部位 | 显示 |
| --- | --- |
| 日志区 | 只有一行「引擎已启动：」（6 个字符） |
| 状态栏左 | `已采集 0 点 \| 请求 0 次 \| 失败 0 \| 已跑 219.1s` |
| 状态栏右 | `引擎：运行中` |
| 按钮 | 「开始压测」灰、「停止」可点 |

**和「k6 正在跑但还没输出」完全一样** —— 而且因为 `finished` 永远不会来，
会**一直停在这个状态**，`m_uiTimer` 也一直跳。

**为什么静默**：M7 之前 `MainWindow.cpp:180-182` 只 connect 了三个信号
（`readyReadStandardOutput` / `readyReadStandardError` / `finished`），
**没有 `QProcess::errorOccurred`**。`FailedToStart` 只发 `errorOccurred`，
不发 `finished` —— 所以收尾逻辑（`setRunning(false)` / 停定时器）永远不执行。

**这正是 M7「异常路径」要处理的东西**，但成本只有 3 行；
在 M2~M6 期间它会让"k6 起不来"这件事**伪装成"压测在跑"**，值得提前补上。

**另外一条实测（与项目无关，仅备查）**：本机某些进程上下文下
（例如自动化工具的 shell）`QProcess` 无论启动什么程序都报同一个 `FailedToStart (pipe: ...)`，
连 `cmd.exe` 也一样 —— 这是**运行环境**的问题，不是代码的问题。
如果你在某个终端里发现所有 `Qt + QProcess` 探针都失败，先在同一个终端里
手工跑一次 `k6 run` 确认 k6 本身可用，再跑 `qprocess_start_check_run.sh` 定位。

#### 补充实测（2026-09-24，同一现象的更完整证据矩阵）

| 实验 | 结果 |
| --- | --- |
| `QProcess::start("C:/Program Files/k6/k6.exe")` | ❌ `FailedToStart (pipe: 系统找不到指定的文件。)` |
| `QProcess::start("C:/Windows/System32/where.exe")` | ❌ **同样失败** → 与 k6、与被测程序无关 |
| `QProcess::start("C:/Windows/System32/cmd.exe")` | ❌ 同样失败 |
| python `subprocess.run(["k6.exe", "version"])` | ✅ `rc=0` → **系统与文件本身正常** |
| 系统命名管道计数 | 709 个（正常量级），其中 Qt 管道 **0** 个 → 资源没耗尽 |
| 换非沙盒方式重跑 | ❌ 同样失败 → 不是沙盒策略差异 |
| 三种路径写法（正斜杠 / 8.3 短名 `PROGRA~1` / 裸文件名） | ❌ 全部失败 |
| 机器启动时间 | 2026-09-24 08:41 —— 重启后出现；前一晚（9-23）同一台机器上是正常的 |

**原理**：`QProcess` 在 Windows 上靠**命名管道**做启动同步。
这个上下文里 `CreatePipe` / `CreateFile` 被拒
（错误码 `231 = ERROR_PIPE_BUSY`、`2 = FILE_NOT_FOUND`），所以**任何**程序都起不来。
而管道总数正常、句柄未耗尽 → 更像**执行上下文的策略限制**，而不是系统损坏。

#### ★ 结论修正（2026-09-24 15:39）：这个状态是**临时**的，会自愈

同一天下午复测，**同一个探针、同一台机器、没改任何代码**，`QProcess` 完全正常：

```
t=   39ms  [started]        pid=30140
t=  304ms  [stdout]         4096 字节
t=  305ms  [stdout]         8192 字节
```

**触发条件：同期有别的重活在抢这台机器。** 用户当时正在桌面自测
（跑自己那份 app + 压测），与本探针的执行环境撞在一起。

| 时间 | 状态 | 界面 e2e 结果 |
| --- | --- | --- |
| 2026-09-24 12:27 | ❌ FailedToStart | `RESULT=ENV_NO_QPROCESS`（守卫拦下） |
| 2026-09-24 15:40 | ✅ 正常 | A1/A2/A3 全 PASS |

→ **判据：一次 `FailedToStart` 不足以怀疑代码，也不足以判定机器坏了 —— 隔几分钟重跑。**
→ 但这**不推翻**本节主结论：`errorOccurred` 没接 = 界面会**静默卡在「运行中」**。
   真实用户点「开始压测」时撞上这个临时状态，看到的就是"压测在跑但没数据"，**M7 那 3 行还得补**。

**★ 遇到 FailedToStart 时，先做这个"三行对照"，再决定是修代码还是换环境**：

```bash
# ① 同一终端手工跑一次 —— 证明系统层可用
"C:/Program Files/k6/k6.exe" version                       # 有输出 → 系统没问题
# ② 换一个"与项目无关的系统程序"进 QProcess —— 证明与 k6 无关
bash tools/probes/qprocess_start_check_run.sh "C:/Windows/System32/where.exe"
# ③ 两边都印证 ⇒ 环境问题，不是代码问题
```

**配套改进**：`m3_e2e_probe.cpp` 开头已加**环境守卫** —— 先试着启动
`C:/Windows/System32/where.exe`，失败就直接 `RESULT=ENV_NO_QPROCESS` 退出。
**没有这道守卫，一个环境故障会被读成"用户的聚合器写错了"。**
这类"**探针必须能区分环境与代码**"的要求，和"断言必须独立于肉眼"是同一族纪律。

### 3.17 「算完不返回」—— 又一条不报错的 bug（2026-09-24，M4 验收）

**现象**：图表标题、坐标轴全部正常显示，但**一条线都没有**。

**根因**：`MetricsAggregator::takeWindow()` 里四步全算对了，最后一行却是
`return WindowSample{};` —— 返回默认构造的空对象，`w` 里算好的东西全部丢掉。
`rps` / `epochMs` 全 0 → 所有点重合在原点 `(0,0)` →
`QLineSeries` 只有一个点 → **画不出线段**。

```cpp
    WindowSample w;
    w.epochMs      = QDateTime::currentMSecsSinceEpoch();   // ← 都在好好算
    w.requestCount = m_stats.requests - m_lastWindowRequests;
    w.rps          = double(w.requestCount) / qMax(1e-3, double(dMs) / 1000.0);
    m_lastWindowRequests = m_stats.requests;                // ← 水位也推进了
    return WindowSample{};                                  // ★ 算了个寂寞
```

**为什么编译器和肉眼都抓不到**：

- **0 警告**：`w` 被赋值过，MSVC 的 C4189（已初始化却未引用）**不触发**
- **0 报错**：返回值类型完全正确
- **界面"看着正常"**：图表、坐标轴、状态栏全都在动

**只有守恒断言抓得到** —— `Σ takeWindow().requestCount` 必须等于输入的总请求数，
返回空对象时它是 0，一对就露。故障注入实测：

| 断言 | 正确代码 | 故障注入（`return WindowSample{};`） |
| --- | --- | --- |
| A1 `ΣrequestCount == 142` | ✅ | ❌ 实得 0 |
| A2 至少一个 `epochMs != 0` | ✅ | ❌ |
| A3 至少一个 `rps > 0` | ✅ | ❌ |
| **A7 曲线 y 值不全为 0** | ✅ | ❌ **「有图没线」的直接判据** |
| A8 `reset()` 后 Σ 仍 == 142 | ✅ | ❌ |

**★ 方法论：探针写完必须做一次「故障注入自证」** ——
把正确代码改回错误版本，确认断言真的翻红。
**没做过自证的断言，等于没有断言**（你只是"相信"它能抓到）。

**同族 bug 清单**（都是"写错了也不报错"，只能靠断言）：

| 里程碑 | bug | 唯一的抓手 |
| --- | --- | --- |
| M3 | `handleLine()` 漏写 `++m_stats.points;` | A3「结束时点数 > 0」 |
| M4 | `takeWindow()` 算完不返回 `w` | A7「曲线 y 值不全为 0」 |

### 3.18 强杀后 `summary.json` **不是消失，是陈旧** —— 本关最阴的坑（2026-09-24 实测）

**背景**：M2/M3 的结论是「`terminate()` 对 k6 无效，只能 `kill()`；强杀后
`--summary-export` 不产出文件」。**这个结论不完整。**

**实测 A/B**（脚本 `docs/evidence/m4/tools/stale_check.py`，可重跑）：

| 实验 | 结果 |
| --- | --- |
| A：正常跑完 3s（`--summary-export` 指向 `stale_summary.json`） | 文件写入，`http_reqs.count = 2184`，mtime `15:41:55` |
| B：**同一路径**跑 30s，第 3 秒 `kill()` | 文件**仍然存在**，内容还是 `2184`，**mtime 还是 `15:41:55`** |
| 判定 | **`VERDICT = STALE`** —— 强杀**既不写、也不删** |

**为什么之前的结论错了**：探针 `m3_e2e_probe_run.sh` 每次跑之前
**自己会删掉 `summary.json`**（第 52 行 `os.remove`），所以它测出来的"强杀后无 summary"
是**被清理过的假象**。真实用户连跑两轮时没人帮他清理。

**后果（比读空文件危险得多）**：

```text
第一轮：正常跑完 → reports/summary.json 写着第一轮的 11701
第二轮：跑到一半点「停止」→ k6 被强杀 → 文件没被刷新
界面读 summary.json → 「存在！解析它」→ 表格里是【第一轮的请求数 + 第二轮的用时】
```

**全程零报错、零警告，数字看起来完全合理。** 属于 3.17 那一族（"写错了也不报错"）。

**正确判据：不是"文件在不在"，而是"引擎是不是正常退出"**：

```cpp
// QProcess::finished(int exitCode, QProcess::ExitStatus status) 里的 status
const bool cleanExit = (status == QProcess::NormalExit);
if (cleanExit) { /* 解析 summary.json */ }
else           { /* 走实时聚合器兜底，并标注"未经 k6 汇总" */ }
```

**★ 通用教训**：**"产物文件存在"从来不等于"产物文件是本轮的"。**
凡是用外部工具的输出文件做数据源，都要问一句：**谁保证它是本轮的？**
答案通常是"退出状态码"，不是"文件是否存在"。

### 3.20 `p(99)` 要靠 `--summary-trend-stats` —— 以及一次**「基准取错」**的翻车记录（2026-09-24）

#### 结论 A：这个参数确实决定 `p(99)` 有没有

| 命令 | `http_req_duration` 的键 |
| --- | --- |
| 不带 `--summary-trend-stats` | `avg, min, med, max, p(90), p(95), thresholds` ← **无 `p(99)`** |
| 带上它（`"avg,min,med,max,p(90),p(95),p(99)"`） | 多出 **`p(99) = 2.996765`** ✅ |

参数值**逗号分隔、不带空格**；只对 summary-export 生效（不影响实时流）。
可以写成两个 argv（`--summary-trend-stats` + 值），也可以写成 `--flag=值`，两种都行。

**本项目 app 自 M2 起就传了它**（`src/K6Engine.cpp:204-205`，两个 `QStringList` 元素）→
**app 真实产出的 `reports/summary.json` 里确实有 `p(99)`**（实测 `p(99) = 8.769`）。
→ **M5 什么都不用改，直接读就有。** 代码注释那句"不加就没有 p99"是对的。

#### ★ 结论 B：一次「基准取错」的翻车记录（这才是本节的重点）

我最初的分析是这样走的：

```text
① 我手敲一条 k6 命令（漏了 --summary-trend-stats）→ 产出没有 p(99)
② 对比语料 tests/corpus/k6_summary_sample.json（有 p(99) / p(99.9)）
③ 得出：『语料 ≠ 生产数据，拿语料单测会全绿、接真实数据才变 —』
④ 并据此给 M5 下发了一个"必须补 --summary-trend-stats"的新步骤（M5-10）
```

**①③④ 全是错的。** 真因只有一句话：

> **我的对比基准是"我自己手敲的等价命令"，而不是"程序真实发出的参数"。**

### 3.21 「有轴、没有线」—— 两个独立成因，都零报错（2026-09-25，M5 重构关）

**现象**：M5 抽完 `ChartContext` 重构出三图后 —— 能编译、能运行、界面正常，
三张图都**有标题、有坐标轴、有网格，就是一条曲线都没有**。0 警告 0 报错。

**判据（像素级，不看截图猜）**：把 `QChartView` 渲染成 `QImage`，
统计 **彩色像素数**（`|max(R,G,B) − min(R,G,B)| > 30`）。
轴 / 刻度 / 标题文字都是灰阶 → 不计入；`QLineSeries` 默认是蓝的 → 计入。
**> 200 才算真的画出了曲线。**

| 组 | `attachAxis` 返回 | 入 chart 后 `attachedAxes()` | 点数 | 彩色像素 |
| --- | --- | --- | --- | --- |
| A：先 `attachAxis` 后 `addSeries`（← 当时的 `src/`） | **false / false** | **0** | 6 | **0** |
| B：先 `addSeries` 后 `attachAxis` | true / true | **2** | 6 | **842** |

同一份数据、同一个 `QChart`，**只换了两行顺序**，结果是一个像素都没有 → 842。

#### ① `attachAxis()` 必须在 `addSeries()` **之后**

Qt 拒绝得毫不含糊，只是它**只用 qWarning 说，返回值被丢弃就什么都看不见**：

```text
[WARNING] Series not in the chart. Please addSeries to chart first.
```

真实 `RealtimeChartView` 的体检结果（喂 10 个样本）：

| chart | series 数 | 点数 | 绑定轴数 | 彩色像素 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 请求速率 RPS | 1 | 10 | **0** | **0** | FAIL |
| 虚拟用户数 | 1 | 10 | **0** | **0** | FAIL |
| 响应时间 | 1 | 10 | **0** | **0** | FAIL |

★ 注意这三行：**轴建出来了**（每张 2 个）、**series 进 chart 了**（各 1 个）、
**点也填进去了**（各 10 个）—— 唯独轴没绑上，于是什么都画不出来。
这正是"零报错但有图无线"的形态：每个零件都在，缺的只是那条连接线。

#### ② 同一族的第二处：`addSeries()` 漏了

`响应时间` 图的 `series 数 = 1`，应该是 **2** —— `m_p95Series` 只调了 `attachAxis`，
**从来没有 `chart->addSeries(m_p95Series)`**。修好顺序后它仍然不会显示。

#### ③ 另一个独立成因：Y 轴范围不含数据（诊断时别把两者混了）

Part C 第一版忘了给 RPS 做 Y 自适应，Y 轴停在初值 `0~100`，
而 RPS 值是 1150~1270 → 曲线被画到**画布外面** → 彩色像素**同样是 0**。

→ **诊断"有图无线"的顺序必须是：先看 `attachedAxes().size()`，再看 Y 轴范围。**
只数像素会把两个完全不同的成因混成一个。

| chart | series 数 | 点数 | 绑定轴数 | 彩色像素 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 请求速率 RPS | 1 | 10 | 2 | 249 | OK |
| 虚拟用户数 | 1 | 10 | 2 | 296 | OK |
| 响应时间 | **2** | **20** | **4** | 537 | OK |

延迟图 2 条 series / 4 个绑定轴（两条线各绑 X、Y）—— **两条线共用一条 Y 轴也正常**。

#### ★ 为什么这批 bug 全都没有任何提示

**Qt 的 `qWarning` 在 Windows 上走 `OutputDebugString`** ——
只有挂着调试器（VS / VS Code 的 Debug Console）才看得见。
直接双击 exe、或在普通终端跑，**一个字符都不会显示**。

→ 这类"API 用错了但返回 false 被丢弃"的调用，**只能靠断言抓**，
和 3.12 ③（漏 `++m_points`）、3.17（算完不返回）是同一个家族：
**凡是不报错就能写错的代码，必须有一条独立的可判定断言兜着。**

### 3.22 `QProcess::errorString()` **会骗你** —— 真错误码藏在 qWarning 里（2026-09-25，M5 界面级验收）

**现象**：`m3_e2e_probe` 一上来就报环境自检失败，屏幕上只有一行：

```
本机 QProcess 无法启动任何子进程（连 where.exe 都起不来）：pipe: 系统找不到指定的文件。
RESULT=ENV_NO_QPROCESS
```

`errorString()` 说 **`pipe: 系统找不到指定的文件。`**（= `ERROR_FILE_NOT_FOUND`）。
顺着这句话排查一个多小时，方向全错 —— 因为**这个错误码是陈旧的**。

#### ★ 关键一步：换个能捕获 stderr 的上下文，真错误才露出来

同一个探针、同一台机器，**把 qWarning 引到 stderr** 再跑，qWarning 立刻出来：

```bash
export QT_FORCE_STDERR_LOGGING=1        # ★ 2026-09-25 更正：QT_LOGGING_TO_CONSOLE=1 已废弃
./out/qprocess_channel_diag.exe 2>&1
```

```
QProcess: CreateFile failed. (所有的管道范例都在使用中。)
QProcess: CreateFile failed. (所有的管道范例都在使用中。)
QProcess: CreateFile failed. (所有的管道范例都在使用中。)
```

= **`ERROR_PIPE_BUSY (231)`** —— 与 `FILE_NOT_FOUND` 完全是两回事。
（三次 = 三种通道模式各失败一次。）

> **为什么必须加那个环境变量**：Qt 在 Windows 上默认把 qWarning 交给
> **`OutputDebugString`**，只有挂着调试器才看得见 —— 直接跑（不加环境变量）时
> **一条都不会出现**（实测对比：不加 = 0 条，加 = 3 条）。
>
> ★ **2026-09-25 更正**：`QT_LOGGING_TO_CONSOLE=1` **已废弃**。再跑它会多打一条
> ```
> warning: Environment variable QT_LOGGING_TO_CONSOLE is deprecated, use
> QT_ASSUME_STDERR_HAS_CONSOLE and/or QT_FORCE_STDERR_LOGGING instead.
> ```
> 功能**仍然生效**（所以上面 0 → 3 的结论没有作废），但**新脚本一律写 `QT_FORCE_STDERR_LOGGING=1`**。
> 同族教训：**照抄旧配方前，先看它有没有打 deprecation warning。**
>
> **为什么会误导**：Qt 的 `QProcessPrivate::createPipe` 失败时调用
> `setErrorString(QStringLiteral("pipe: ") + qt_error_string())`，
> 而 `qt_error_string()` 取的是 **`GetLastError()` 的当前值** —— 它可能是更早某个
> 无关调用留下的陈旧值。真正的失败原因只写在 `qWarning` 里。
> 同族于 §3.21 那条「Qt 的拒绝理由只有挂调试器才看得见」。
>
> **纪律**：**先把 qWarning 弄出来，再信 `errorString()`。**
> 通用配方：**跑 Qt 探针时一律加 `QT_FORCE_STDERR_LOGGING=1` 并 `2>&1`。**

#### 环境和代码都排除了（三组独立对照）

| 对照 | 做法 | 结果 |
| --- | --- | --- |
| **① 纯 WinAPI（python ctypes）** | `CreatePipe` / `CreateNamedPipeW`（1 实例 & 255 实例）/ `CreateFile` 连接 / `ConnectNamedPipe` / `\\.\NUL` | **全 OK**。建完立刻连 200/200 OK；建完等 0.5 s 再连 20/20 OK；连建 3 个 OK |
| **② 全新未签名的 C++ exe** | 同样的管道序列 + `CreateProcessW(where.exe)` | **全 OK**（`cmd.exe` 的路径都打印出来了）→ 不是"未签名程序被安全策略拦" |
| **③ 命名空间对照** | 不启动任何 Qt 程序时枚举 `\\.\pipe\` | `qt-*` 管道 **0 个** → 观测到的 `qt-*` 确实是 Qt 建的 |

Qt 建的管道名实测长这样（一次运行一个）：`qt-44C0-31B42425`、`qt-51E0-CF185A5A`、…
`qt-<pid16进制>-<8位hash>`，**每次运行都不同** → 排除"名字撞上残留管道"。
（管道名模板从 `Qt6Core.dll` 的 UTF-16 字符串里挖出来的：`\\.\pipe\qt-%lX-%X`，旁边还有 `\\.\NUL`。）

#### 三个证据把"项目代码"也排除掉

| # | 证据 | 结论 |
| --- | --- | --- |
| 1 | 三种通道模式 **`SeparateChannels` / `ForwardedChannels` / `MergedChannels`+输出到文件**，**全部同样失败** | 失败的不是 stdout/stderr 通道 —— 是 Qt **无条件创建**的那个启动同步管道。`ForwardedChannels` 根本不建通道管道，照样失败 |
| 2 | 把探针复制到**全新路径 + 全新文件名**再跑 | 照样失败 → 不是命名残留 / 不是可执行文件身份问题 |
| 3 | 只有 `CreateFile failed` 这条 qWarning 出现；`CreateNamedPipe failed` / `ConnectNamedPipe failed` **一条都没有** | `CreateNamedPipe` 是**成功**的 → 失败在**客户端连接**那一步 |

#### 根因

环境变量里赫然有：

```
LSBOX_AUDIT_SHMEM=Local\LiteSandbox_Audit_25876_25085656
CODEBUDDY_ENABLE_SECURITY_AUDIT=1
```

→ 整个进程树跑在 **LiteSandbox** 里。`dangerouslyDisableSandbox` 只影响**单条命令**，
抬不掉进程树继承下来的这一层。而这层拦截/占用了 Qt 启动管道那个**单实例**命名管道，
于是 Qt 的客户端 `CreateFile` 拿到 `ERROR_PIPE_BUSY`。

**结论：与项目代码无关，是执行上下文层面的拦截。** 与 §3.16 的结论一致，
但这次给出了**精确机制**，并且说清了**为什么旧结论里的 errorString 是误导性的**。

#### 影响面与应对

| 受影响 | 影响 | 应对 |
| --- | --- | --- |
| `m3_e2e_probe` / `m2_e2e_probe` | 直接报 `ENV_NO_QPROCESS` 退出（守卫工作正常，**不误报成代码缺陷**） | 界面级验收改用 `m5_ui_probe`（**不依赖 QProcess**，用 `QMetaObject::invokeMethod` 驱动真实 `MainWindow` 的槽） |

### 3.23 「能不能起子进程」**不是布尔值** —— 三个方式 × 两种上下文（2026-09-25 追加）

§3.22 只回答了「为什么失败」。本节回答**「有没有能成的方式」** —— 因为它不是一个是/否问题，
而是**三种启动方式 × 两种执行上下文**的一张矩阵。花一小时之前先看这张表。

探针：`tools/probes/qprocess_startdiag.cpp`（五路对照，全部起同一个 k6）

| 启动方式 | 沙箱内（默认） | 无沙箱 |
| --- | --- | --- |
| 裸 `CreateProcessW`（+ 重定向到文件） | ✅ **能起** —— `exitCode=99`，stdout 21,135,583 字节 | ✅ 能起 |
| **`QProcess::start()`** | ❌ `ERROR_PIPE_BUSY(231)`；三种通道模式**全部**失败 | ✅ **完全正常** —— `waitForStarted=1 / state=2 / finished exitCode=99 / 1213ms` |
| `QProcess::startDetached()` | ✅ **能起** —— 71,693 行 k6 JSON | ✅ 能起 |

> ★ **注脚（2026-09-26 补）**：沙箱内 `start()` 那个 ❌ 的准确含义是
> **「Qt 认为启动失败」**，而**不是「子进程没被创建」**。
>
> 实测证据：探针退出时 Qt 自己打了一条
> `QProcess: Destroyed while process ("C:\Program Files\k6\k6.exe") is still running.`
> —— 说明 k6 **真的被创建了、真的在跑**，只是命名管道握手那一步失败了。
> （另外 `QProcess::startDetached()` 在沙箱内能成，也侧面说明 `CreateProcess`
> 这一层从来没被拦过。）
>
> **后果很实际**：这种"孤儿 k6"会在你的探针**退出之后**继续跑，并在结束时写
> `--summary-export` 指定的文件 —— 足以冲掉任何 backup/restore 逻辑
> （实测把用户 `reports/summary.json` 从 4168 B / 1980 请求冲成 3290 B / 8 请求，
> 详见 §3.25 末尾）。
>
> **所以：判断"k6 起来了没有"不能只看 `errorString()` 和状态机，要去看进程列表。**

#### 无沙箱那次的完整证据（这是"代码没问题"的铁证）

同一个探针、同一个 exe，只把沙箱摘掉，**五路全绿**：

```
[1] raw CreateProcessW   STARTED. exitCode=99    stdout 19,482,173 B / stderr 1,176,009 B
[2] QProcess::start()    waitForStarted=1  state=2  finished exitCode=99  elapsed=1184ms
[4] Separate/Forwarded/Merged 三种通道模式    全部 waitForStarted=1
[5] startDetached(static) + k6 自写文件        pid=33040  结束  exitCode=99
                             sd2_metrics.json 38,534,320 B / sd2_summary.json 2,846 B
```

→ **唯一的变量是沙箱。** 被启动的程序、参数、通道模式、项目代码，一项没变。
（`exitCode=99` 是 k6 的「阈值被突破」退出码，不是错误 —— stderr 末尾的
`level=error msg="thresholds on metrics 'http_req_failed' have been crossed"` 才是它的来源。）

**归档**：`docs/evidence/m5/qprocess_start_matrix_NOSANDBOX_20260925.txt`
（原始输出 10,657 行，已滤掉 10,572 行 k6 `Request Failed` 噪声 —— 被测目标 `127.0.0.1:8918`
没起服务，每个请求打一条；那 1 万多行恰好反证 **k6 真的在跑并且打满了 VU**）
**真实产物**：`docs/evidence/m5/k6_real_summary_20260925.json`
（就是第 [5] 路那个 `sd2_summary.json`；含 `thresholds` 双条、`passes`/`fails` 反语义、
`value: 1` —— 可直接当 M6 报告的真实语料）

#### 三条可直接用的推论

1. **失败点精确定位在 Qt 那根「启动同步命名管道」**，与 `CreateProcess`、与 k6、与项目代码无关。
   `ForwardedChannels` 根本不建通道管道，照样失败 —— 排除了"通道管道"这个嫌疑。
2. ★ **沙箱内仍有可用路径：`QProcess::startDetached()`**。它不建同步管道，所以能起。
   代价是拿不到实时 stdout（不能 `readyRead`），但可以**让子进程自己写文件**：
   ```cpp
   qint64 pid = 0;
   QProcess::startDetached(exe, args, workdir, &pid);   // ★ 静态版才给 pid；成员版 processId() 拿到 0
   // args 里带：  -o json=<file>   --summary-export=<file>
   ```
   实测产出真实的 k6 输出（17:36 那次沙箱内运行：`detached_stdout.txt` 71,693 行 k6 JSON；
   本次 17:42 无沙箱运行：`sd2_summary.json` 2,846 B，已归档为 `k6_real_summary_20260925.json`）。
   **可以拿它当"真实 k6 产物"喂给下游做验收**，比手搓固定语料可信得多。这条对 M6 报告验收直接有用。
   > ⚠️ 置信度说明：`startDetached` 在**沙箱内**能成，来自 17:36 那次运行（`LSBOX_AUDIT_SHMEM`
   > 当时仍在，输出落在 `detached_stdout.txt`）。**本轮想再归档一次沙箱内版本时，同一段命令
   > 自动升级成了无沙箱** —— 所以归档文件是**无沙箱**版。沙箱内那一版的证据是当时那次的
   > 产物文件本身，未单独归档。
3. **判据一行**：`env | grep -E '^(LSBOX|SANDBOX_CENTER)'`。有输出 = 在沙箱里；
   `(unset)` = 已脱沙箱。**不要靠猜，先跑这一行。**
   另一处佐证：命令输出尾部会出现 `⚠️ Sandbox bypassed (escalation-approved)`。

#### 关于提权（本轮实测，别在这上面耗时间）

- 沙箱**逐条命令**生效。上一条命令拿到过脱沙箱执行，**下一条默认又回到沙箱里**（实测复现两次）。
- 主动声明"关沙箱"**不一定落到这条命令上**；真正管用的是**用户在弹出的权限提示上点允许**。
  所以需要脱沙箱时，**把话说清楚请用户点**，不要反复重试同一段命令 —— 重试的结果仍然在沙箱内，
  而且会被误当成"无沙箱也不行"。
- **但"同一段命令再跑一次"反而容易触发自动升级**：本轮实测，17:36 那次的沙箱内结果与 17:42 那次
  的脱沙箱结果来自**完全相同的命令**。所以看到 `env LSBOX_AUDIT_SHMEM = (unset)` 时，

#### 附：`QLineSeries` 漏掉几秒的 x，线会**断开**吗？（`series-gap` 模式）

x = `1,2,3,7,8,9`（第 4/5/6 秒没有数据点），Y 恒 50，X 轴 0~10。

```

### 3.25 写文件这一族：六个坑全是"不报错但写错"（2026-09-26，M6 报告关）

验的是 `ReportWriter.cpp` 的三个函数。探针 `tools/probes/m6_report_probe*`
（**37 PASS / 0 FAIL** —— 经 4 轮收敛，13 FAIL → 0），
原始输出 `docs/evidence/m6/m6_report_probe_20260926.txt`。
下面六条都有**独立可判定断言** —— 因为它们的共同特征就是**不崩、不报错**。

#### ① `QIODevice::Text` 会把 `\n` **偷偷换成 `\r\n`**

```cpp
if (!file.open(QIODevice::WriteOnly | QIODevice::Text))   // ★ 就是最后这个标志
```

契约写的是"换行用 `\n`"，但 `QIODevice::Text` 在 Windows 上启用**换行转换**。

实测（同一个 `buildMarkdown` 的输出）：

```
文件 31709 B  vs  预期 31686 B      →  多 23 字节
文件里 \r 出现 23 次               →  24 行的报告恰好 23 个 \n
```

**差值和行数一模一样**，这就是"每个 `\n` 都被多塞一个 `\r`"的指纹。
（把 `\r\n` 归一化成 `\n` 之后字节数**完全相等** = 31686 —— 内容没丢，只是换行被换了。）

- **判据**：读回文件，`body.count('\r') == 0`。
- **副产品**：这个 23 字节的差值会**掩盖**真正的"内容被截断"问题 —— 两件事必须**分开验**
  （先归一化再比字节数），否则一个 FAIL 里混着两个成因，修起来会改错地方。

#### ② `file.close()` 早于 `QTextStream` 析构 —— Qt 亲口作证

```cpp
QTextStream out(&file);
out << buildMarkdown(result);
file.close();          // ★ out 还活着，它的内部缓冲此刻无处可去
```                                                // ← out 在这里析构，才想 flush

构造顺序是 `file` → `out`，析构顺序反之，所以**显式 `close()` 排在 `out` 析构之前**。
实测 Qt 直接打了一条：

```
QIODevice::write (QFile, "…\blocker.txt\…md"): device not open
```

- **判据**：这一路无法直接断言，改用**内容完整性**对账 —— 写一段 >16KB 的内容
  （`QTextStream` 内部写缓冲是 16KB），比较落盘字节数与 `buildMarkdown` 的预期长度。
- ★ **当前为什么侥幸没丢**：代码里是**一次性** `out << 整段字符串`，一次写入就把缓冲全刷了。
  一旦改成**多次** `<<`（比如按小节拼），尾巴就会丢。这是**潜伏**的，不是"已经正常了"。
- **修法**：让 `out` 先出作用域（加一层 `{}`），或 `out.flush()` 之后再 `close()`。

#### ③ 失败路径**照样返回一个路径** → 调用方无法区分成功失败

```cpp
if (!QDir().mkpath(outputDir)) { if (errorOut) errorOut->append(…); }   // ★ 没 return
if (!file.open(...))           { if (errorOut) errorOut->append(…); }   // ★ 没 return
…
return filePath;                                                        // ★ 无条件返回
```

实测：把 `outputDir` 指向一个**已存在的文件**（目录永远建不出来）→

```
返回 = "E:/…/blocker.txt\benchboard-20260921-152400.md"     ← 非空！看着像成功
err  = "无法创建目录: …无法创建文件: 系统找不到指定的路径。"   ← 原因有，但只有传了 errorOut 才拿得到
```

调用方（`onExportClicked`）收到非空路径就打印"**已导出：…**" —— 而磁盘上什么都没有。

- **判据**：`writeMarkdown(...)` 的**返回值必须为空串**，`errorOut` 非空。两个都要断言。
- **同族的第二处**：`onExportClicked` 把 `err` 收下来**从不使用**（`MainWindow.cpp:225-229`）。
  "错误信息收了不用"和"没收"是一回事 —— 这是个**两层的静默失败**。

#### ④ ★ 有默认值的字段，"非空"是**弱判据**（假通过）

`TestConfig` 自带 NSDMI：

```cpp
QString targetUrl = QStringLiteral("http://127.0.0.1:8899/");
int     vus       = 10;
QString duration  = QStringLiteral("30s");
// scriptPath / k6Path / outputDir  —— 没有默认值
```

于是 `TestRunResult{}` 里 `config.targetUrl` **永远非空**。报告里看到的
`目标 URL: http://127.0.0.1:8899/` 看着完全正常，**其实是从没被赋过值的默认值**。

探针的三种判据对比（背后是同一个"`buildRunResult` 没接线"的事实）：

| 判据 | 结果 |
| --- | --- |
| "目标 URL 非空" | **PASS** ← 被默认值骗过，假通过 |
| "脚本路径 非空" | FAIL ✅（该字段无默认值可骗） |
| **"目标 URL == 本次 UI 输入"** | **FAIL ✅** ← 最强：把输入框改成 `http://unique-probe-host-12345/`，报告里仍是 `…:8899/` |

```

```

- **纪律**：验收某条"接线"时，判据要写成**「等于本次输入」**，而不是"非空/有值"。

#### ⑤ 一条**有用的事实**（不是坑）：`SummaryParser` 不碰 `config` / `startedAt`

**不覆盖** `config` 和 `startedAt`。所以"先在 `TestRunResult` 里填好 `config`/`startedAt`，

| 形态 | `grep -v '//'` 干了什么 | 后果 |
| --- | --- | --- |
| **真用 + 行尾注释** | 该行含 `//` → **被删掉** | ★ **假阴性**：把要证明的东西删了 |
| **跨行块注释的内部行** | 内部行不含 `//` → **被留下** | ★ **假阳性**：把噪声当成证据 |
| 行首 `//` 注释 | 被删掉 | ✅ 这一类确实救得了 |
| 单行 `/* */` | 同行若无 `//` 则留下 | ❌ |
| 字符串字面量里的 `"QProcess"` | 同上 | ❌ |

★ **按"行里有没有 `//`"过滤，等于拿一个和语义无关的字符当判据。**
它同时产生假阴性和假阳性 —— 比不做过滤更危险，因为**它看起来像做了处理**。

#### 第二形态：换成 `#include <QProcess>` 照样中招

```
  [FAIL] C2 编排层不 include <QProcess>
  [FAIL] C3 界面不 include <QProcess>
  [FAIL] C4 ★★ 全仓只有 K6Engine.h 认识 QProcess
         实际 = K6Engine.h, LoadEngine.h, MainWindow.cpp, MainWindow.h, TestOrchestrator.cpp
```

原因很讽刺：**探针自己的注释**里写着"正解是删掉 `#include <QProcess>` 后仍能编译" ——
这句话本身被当成了命中。（真命中只有 `K6Engine.h:38`，另外 4 处全是注释。）

#### 正解两条，任选

1. **剥掉注释再比** —— `m7_engine_probe.cpp` 的 `stripComments()`：处理 `//`、`/* */`、
   字符串字面量，并**保留换行以维持行结构**（不留换行，行号就对不上了）。
   实测 **19/19 全过**。
2. **让编译器判** —— 把 `#include <QProcess>` 从被测文件里删掉，**看还能不能编过**。
   真用了代码，编译器替你抓；注释里爱怎么写怎么写。**这条更硬**（判语义而非文本），
   代价是多一次编译。

★ **可推广的三句**：

1. **判据自己也是要验收的东西。** 一条"永远过不了"的判据，和一个"永远过"的判据一样糟 ——
   它们都会让你停止思考。
2. **凡是"读源码文本"的判据，默认先剥注释。** 注解里写什么都合法。
3. **过滤型修补要拿正反例各验一次。** 只验证它删掉了噪声（假阳性）、不验证它没删掉真信号
   （假阴性），就会得到 `grep -v '//'` 这种"看起来在干活"的东西。
